
# ADR-000 — Ingest legacy order export by fixed-width slicing with explicit rejection

**Status:** accepted
**Date:** 2026-09-17

## Context

The order export (`orders-20260901.txt`) and the customer master (`customers.csv`)
come from a system nobody controls, in a format that predates any negotiation
about interoperability. Two specific things bit hardest:

- **Two different encodings in one integration.** The order file is CP1257
  (`windows-1257`), the customer CSV is UTF-8. Reading the order file with
  `readFileSync(path, "utf8")` does not throw — it silently produces garbled
  names (`Bērziņš` becomes `B?rzi??` or similar) while every column position
  stays intact, so the record still looks structurally valid. Nothing in the
  output signals the corruption; you have to know to check for it.
- **A truncated record with no error signal.** Line 6 of the order file
  (`ORD-0006  C0000006  Ilze V`) is only 26 characters long instead of 77.
  Slicing it by fixed column position either throws (out-of-range) or, worse,
  silently returns whatever partial substring happens to exist at those
  indices — which would have looked like a real, if odd, order.

The comma decimal separator (`45,20`) and the trailing zero-padding on every
field were also traps: routing the amount through `parseFloat` collapses
`"45,20"` (misread as `45` then `.20` lost, or `NaN` depending on how you
strip the comma) and drops trailing zeros (`"7800,00"` → `7800`), which is
silent data loss on money. Order `ORD-0004`'s amount is negative (`-250,00`,
a refund) — an easy value to accidentally filter out if you assume amounts
are always positive.

## Decision

`ingest()` reads the order file as raw bytes (`readFileSync` with no encoding
argument) and decodes it explicitly with `new TextDecoder("windows-1257")`
via `decodeOrderFile()`, rather than trusting Node's default UTF-8 read. Each
line is validated against `ORDER_LINE_LENGTH` (77) before any field is
sliced; a line of the wrong length is pushed to `rejected` with its 1-based
line number and a reason string, and processing continues rather than
throwing. Fields are extracted by fixed column position (`ORDER_LAYOUT`),
never by splitting on whitespace, since `customerName` contains internal
spaces.

`amount` is kept as a string end-to-end: `toDecimalString()` only replaces
the decimal comma with a period (`"45,20"` → `"45.20"`) and never routes the
value through `Number` or `parseFloat`, so trailing zeros and the sign survive
intact. `orderDate` is converted from `DD.MM.YYYY` to `YYYY-MM-DD` in
`toIsoDate()` via plain substring slicing, deliberately avoiding
`new Date(...)`, which would have introduced an unwanted timezone and
ambiguous day/month parsing.

`parseCustomers()` reads the CSV as UTF-8 (its actual encoding), skips the
header row, and builds an id → name map. `unmatchedCustomers` is computed as
the set difference between all customer IDs in the CSV and the set of
customer IDs that appear on at least one accepted order.

## Alternatives considered

**Adding `iconv-lite` for the CP1257 decode.** Rejected because
`TextDecoder("windows-1257")` is already built into the Node/V8 standard
library and does the same job with zero added dependency surface — and the
assignment explicitly forbids parsing/encoding dependencies for exactly this
reason.

**Asking the upstream system for a JSON or API-based export instead of
parsing this file at all.** This is the alternative most worth taking
seriously for a 5-year system. A file-based export with an undocumented,
unversioned fixed-width layout is inherently fragile: there is no schema, no
validation, and no way to distinguish "the format changed" from "the format
is broken" except by a human noticing the report looks wrong. It was rejected
for this assignment because the whole point was to build the resilience by
hand — but for a production integration I would push hard for a contract
(even a documented CSV with a header, or better, a small internal API) rather
than accepting an ad hoc byte layout as a permanent interface.

**Storing `amount` as a `number` and formatting it back to a string on
output.** Rejected because floating-point numbers cannot represent decimal
currency values exactly, and the round trip through a float is precisely
where trailing zeros and precision get silently lost — the entire failure
mode `toDecimalString()` exists to avoid.

## Consequences

Rejecting malformed lines instead of throwing means the pipeline is
resilient to a single bad record, but it also means a systematic corruption
(e.g. the whole file arriving one byte short of the layout, or an off-by-one
column shift) would show up as *every* record being rejected rather than a
loud early failure — the `rejected` array needs to be monitored, not just
generated.

If the upstream system adds a field in the middle of the record, every column
offset after that point silently shifts, and the fixed-width parser will
happily slice the wrong bytes into the wrong fields without erroring; this
implementation has no defense against that beyond the per-line length check,
which would only catch it if the new field also changes the total line
length. If a customer name legitimately exceeds 32 characters, it will be
silently truncated rather than rejected, since the parser trusts the layout's
column boundaries rather than validating name length against padding. If
someone sends the file as UTF-8 by accident, decoding it as CP1257 will not
throw — most CP1257 code points overlap with Latin-1/UTF-8's single-byte
range — so this would silently corrupt correctly-encoded names in the
opposite direction, a failure mode this implementation does not detect.

The cost accepted here is that correctness depends entirely on the upstream
system never changing its byte layout without telling anyone; nothing in this
code would catch that early.
